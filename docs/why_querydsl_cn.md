## 什么是 QueryDSL

[QueryDSL](https://github.com/querydsl/querydsl) 是一个历史悠久的查询构建器，基于 SQL 抽象语法树建模。

在 Hibernate 和 JPA 大行其道的年代，开发者很快发现 ORM 无法表达稍微复杂的查询。Hibernate 引入了 HQL，JPA 引入了 QueryBuilder 和 NativeQuery，但这些方案都不完美。大约 2015 年，我在为 GeeQuery 适配 Spring-Data 时，发现 Spring-Data 引入了 QueryDSL 作为新的查询构建器。

QueryDSL 的核心价值：

- **表达力强**：对 SQL 词法树建模，几乎能涵盖 SQL 的所有功能。它还用相同方法为 Lucene、JPA、ES、JDO、MongoDB 等进行了查询建模。
- **类型安全**：编译期即可检查查询语法和字段引用。相比之下，直接使用 JSON、SQL、HQL、JPQL 等查询语言只能基于字符串拼接——对于长期维护的业务项目，这是非常危险且繁琐的。开发者无法确认改对了没有，也无法确认所有需要修改的位置都得到了修改。
- **API 友好**：接近 SQL 且符合自然语言习惯，代码可读性强、无冗余。

试用后我发现 QueryDSL 的潜力巨大，可以说是一个理想的数据库 Facade。在此基础上，我对对象构造与反射等场合做了重写以追求极致性能，就有了这个框架。

## 为什么选择本框架

### 来自 QueryDSL 的优势

- 最友好的 Query API 之一，很多 JPA 使用者已经熟悉其用法。
- SQL 特性覆盖极为全面，是除了直接操作 SQL 语句之外灵活性最强的框架。
- 编译期类型检查，项目维护成本可控。与 xxQL 路线不同，Query API 路线天然具备类型安全。
- 良好的跨数据库移植性支持。

### 来自本框架的增强

- **极致性能**：ASM 动态生成字段访问器，消除反射开销。批量操作可达 MyBatis 的 3–8 倍。
- **单表 CRUD**：GenericRepository 封装了常用增删改查，简单场景开发效率不输 JPA。
- **DDL 管理**：支持表结构分析、对比、自动更新。通过包扫描，具备类似 Hibernate 的启动时 schema 维护能力。DDL 能力也作为 API 开放给开发者使用。
- **纯 POJO 模式**：无需生成 Q-class，通过 Lambda 引用列，降低使用门槛。
- **实用功能**：业务分表路由、表初始化数据导入等，将开发者与 SQL 语句彻底切割。

### 其他考量

- 提供原始 Connection 对象，兼容必须使用 JDBC/SQL 的场景。
- 互联网行业几乎都放弃了 JPA 路线，转入 JDBC 和 MyBatis 路线（参见附录），因此失去了类型安全和编译期检查。本框架的重要意义在于——让这些开发者重新获得类似 JPA 的开发效率和编译期检查能力。
- 本框架还提供了跨数据库移植特性。虽然互联网行业普遍不看重这一点，但谁能保证未来不做私有化的 ToB 业务呢？
- 如果选择 Query API 路线，本框架可能是最佳选择。

## 为什么可以用 QueryDSL 代替 JPA

大部分了解 QueryDSL 的开发者是通过 JPA 接触它的，认为它只是 JPA 查询的补充。这里解释一下为什么可以完全替代。

我本人也是从 JPA 路线转换过来的，过程大致如下：

1. 使用 MyBatis：在一个 8 人团队、配备开发 DBA 的两年维护项目中，频繁优化数据库结构和查询语句。多人修改的、分散的、大量多表关联的 SQL 片段，由于没有编译器和类型安全检查，耗费了团队极大精力。
2. 使用 JPA 和 JPQL/QueryBuilder（从流行实现逐步更换为自有 JPA 实现 GeeQuery）。
3. 使用 Spring-Data，发现并使用其引入的 QueryDSL 作为查询构建器。业务代码可读性很强，尤其是很好地解决了编译期检查问题。
4. 某天想到：querydsl-jpa 已经能处理复杂查询，而 JPA 提供的无非是单表 CRUD、级联和延迟加载。把单表 CRUD 封装一下几乎没有难度，级联和延迟加载也不是非要不可——那还留着 JPA 干什么？

以下逐一分析 JPA 的特性及本框架的替代方案：

**单表操作（save/merge/load/update）**

GenericRepository 提供了等价 API，无需自行拼装 query 对象。→ **可替代**

**复杂多表查询**

在 JPA 中也是用 QueryDSL 语法构造，切换后没有任何变化。→ **可替代**

**NativeQuery（特别复杂的统计类 SQL）**

本框架未提供 NativeQuery 特性，建议使用 Spring-JDBC 代替。Spring-JDBC 用法更为广泛，也能完成对象映射等基本功能。本框架能与 Spring-JDBC 共享同一个事务。→ **可通过补充方案解决**

**LOB 延迟加载**

从实际用法看，绝大多数情况下，执行查询之前业务是否需要 LOB 字段已经是明确的。延迟加载将一次数据库交互变成两次，并不是好做法。JPA 需要这个特性是因为无法精确指定 SELECT 列，而 QueryDSL 可以灵活指定需要的列——需要就查，不需要就不查。与其说是特性，不如说是对 JPA 自身缺陷的补偿。→ **用指定字段查询替代**

**级联（@OneToOne/@OneToMany/@ManyToOne/@ManyToMany）**

这是一个提升开发效率的好功能，但支持级联后性能风险大幅增加。企业和小型项目用的不少，互联网行业基本不用。本框架以性能为优势，更推荐给性能敏感的大型项目。今后可能以 SPI 方式扩展支持。→ **今后考虑扩展**

**L1/L2 Cache**

本框架不实现对象缓存，理由如下：

- 设计理念是轻量、易掌握、可观测性强。框架应尽可能暴露数据库能力，而不是在中间做额外的事情。
- 分布式应用中多实例并发访问很常见，数据库层缓存会把问题搞复杂。
- 数据库不提供可重复读的场景下，框架也不应去做改变数据库行为的事情。
- 现代缓存框架很多（Spring Cache + Caffeine/Redis 等），贴近业务的粗粒度缓存比数据库层缓存有效得多。框架没有必要干预架构师的缓存决策。

→ **用业务级缓存代替**

## 项目历程

这个框架可以说是无心偶得，今后也会佛系维护。

- **2017**：有了替换 JPA 的想法后说干就干，去除 JPA，仅留下 querydsl-sql 模块。对 QueryDSL 的监听行为进行扩展，获取更详细的日志信息。
- **2018**：性能演进。对反射操作进行优化，引入 ASM 自动生成动态类完成字段拼装，无反射调用。框架正式诞生。
- **2019–2023**：自用阶段，对常用功能进行小改使代码更简洁，如自动时间戳、自动生成 GUID 等。
- **2024**：阅读源码时发现原作者一开始想支持 DDL 语法但后来放弃了。由于早年在 GeeQuery 上写过相关功能，花了不少时间支持了 DDL 语法。另外增加了无 Q-class 的纯 POJO 用法来降低使用门槛。
- **今后**：保持轻量是维护宗旨，不会加入乐观锁、词法分析器、分库分表、内置连接池之类的东西——虽然都写过，但糅合在一起没有必要。

> 如果觉得不错，无需给本项目 Star，请 Star [QueryDSL](https://github.com/querydsl/querydsl) 项目。好的设计都来自 QueryDSL，我只是做了一些微不足道的增强。

## 附：Java 数据库访问技术路线对比

### JPA 路线

该路线对单表应用和小规模企业应用的开发者较为适合。但要精通需要专门学习框架自身知识体系——HQL/JPQL/QueryBuilder/QueryDSL-JPA/SpringData-JPA/Hibernate 的对象管理和缓存机制等。

问题在于：技术栈很深，但和数据库设计、SQL 优化不在一个方向上。抽象的 JPQL 为了兼容所有 RDBMS，有很多限制，无法最大化利用数据库特性（如 RowId、窗口分析函数等）。

| 维度 | JPA/Hibernate | Spring Data JPA | QueryDSL-JPA |
|---|---|---|---|
| 介绍 | 纯面向对象的数据访问。需要 HQL/JPQL/QueryBuilder 完成复杂查询。入门易精通难 | Spring 对 JPA 的封装，保留 JPA 所有功能 | 搭配 Spring Data JPA 使用，该路线的终极方案 |
| 优点 | 单表操作简便；级联/延迟加载无需编码 | JPA 全部优点 + 方法名自动代理 + 引入 QueryDSL 作为查询构建器 | 前者全部优点 + 复杂查询构建方便 |
| 缺点 | 自由度低；性能依赖缓存；多实例缓存刷新问题 | 本质仍是 JPA，精通成本高 | JPA 全部缺点 + 三套框架学习成本 |

### JDBC 路线

| 维度 | Spring JDBC/JDBCTemplate | querydsl-sql | querydsl-sql-extension（本框架） |
|---|---|---|---|
| 介绍 | Spring 对 JDBC 的封装，帮助完成简单映射 | 对数据库和 SQL 特性建模，内部使用 AST 描述数据库访问请求 | 在 querydsl-sql 基础上封装，保留其全部特点 |
| 优点 | 方法名自动代理 | 无需编写 SQL，无需字符串拼接；提供各种结果映射；通过 AST + 方言模板实现跨数据库移植 | querydsl-sql 全部优点 + 极致性能 + 单表 API + Lambda 模式 |
| 缺点 | 封装程度低；需掌握 SQL 和 JDBC；复杂映射需自行处理 ResultSet；无移植性支持 | 简单操作也需编码，效率不够高 | 暂无级联/延迟加载（提供了便捷的多表 Join Query 和数据返回映射） |

querydsl-sql 是所有 JDBC 路线框架中唯一同时做到以下两点的：
1. 开发者无需编写任何 xxQL（HQL/JPQL/SQL），仅需一套 API 即可完成几乎所有数据库操作。
2. 开发者无需接触 JDBC API，无需自行处理结果映射。

### MyBatis 路线

这条路线基于 MyBatis 而非直接使用 JDBC。进入这条路线基本可以放弃数据库可移植性——MyBatis 核心是 SQL 字符串拼接而非 AST，最终数据库访问模型用 SQL 字符串表达。虽然有 SQLParser 等工具试图提升移植性，各种上层框架也采用了类似 AST 的模型来表达复杂查询，但底层架构决定了这条路线的上限。

> 当然数据库可移植性不一定要在访问框架层解决，还可以通过 JDBC 驱动（驱动中词法分析修改 SQL）、中间件（解析数据库网络协议）、多语言数据库（语法兼容模式）来解决。

| 维度 | MyBatis | MyBatis Plus/Flex |
|---|---|---|
| 优点 | 简便、流行、易学、轻量、性能不错 | 增加了 Query API 和代码生成机制（类似 Q-class 或 Lambda 模式），提升开发效率 |
| 缺点 | 无数据库移植性；手写 SQL 效率低；无编译期检查 | 仍需部分 SQL 片段；其他 MyBatis 缺点依然存在 |

### 理想的 SQL 持久层框架

JPA 的优缺点都很突出：
- 优点：开发效率高、类型安全、支持编译期检查的 Query API
- 缺点：性能差、学习成本高、过于重量、结构复杂带来优化与排障难度

理想形态 = JPA 的开发效率和类型安全 + 轻量实现 + 贴近原生数据库（SQL 和 JDBC）。

MyBatis Plus/Flex 等新框架的流行，正是因为在 API 层面集中了上述两条路线的优点。本框架的目的与之一致——基于 QueryDSL，API 与 JPA 开发者使用的基本完全一致，同时保持轻量实现和极致性能。
